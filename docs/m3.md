# Phase 1 / M3 — Real agent execution

M3 connects real (still trusted, host-process) Python agents to the M2 evaluation loop through a
Tool Broker that enforces allowlists, argument schemas, per-tool timeouts, and call budgets.
Scripted actors from M2 keep working unchanged.

## Acceptance criteria

- [x] `AgentAdapter` protocol, `AgentContext` (run_id, seed, fixed_clock, tool_names, emit) and
      `AgentResult` (output, summary, usage) (`agents/protocol.py`); `PythonAgentAdapter` loads
      async `module:function` entrypoints and normalizes raw returns (`agents/python_adapter.py`).
- [x] `Tool` / `ToolProvider` / `ToolRegistry` (`tools/protocol.py`, `tools/registry.py`);
      providers build tools from the `EnvironmentHandle` (dynamic service URLs).
- [x] `ToolBroker` chain in exact design order: allowlist → JSON Schema argument validation →
      atomic budget decrement → `tool.call.started` → per-tool timeout → serializability check +
      key redaction → `tool.call.completed` / `tool.call.failed`; rejections emit
      `tool.call.rejected` and never reach the environment (`tools/broker.py`).
- [x] JSON Schema validation via the `jsonschema` package (new runtime dependency; listed in
      design §5.1 and unavoidable for correct draft-compliant validation).
- [x] Per-tool timeout (`asyncio.wait_for` → `TOOL_TIMEOUT`) and `max_tool_calls` budget consumed
      at call start without an intervening await, so timed-out/failing calls still count.
- [x] Agent wall time via `asyncio.timeout`; timeout → `agent.timed_out` event +
      `AGENT_FAILURE/AGENT_TIMEOUT` attribution, then final state capture and grading continue.
- [x] Agent events: `agent.started/completed/failed/timed_out/message/model.usage`;
      `agent_output` and structured `usage` (tool_calls counted; unknown model metrics stay null)
      land in `result.json`.
- [x] Python agents wired into the Compose flow next to scripted actors; manifest components and
      `Usage` recorded; `--seed` on `reprocase run`.
- [x] Support World Tool Provider (`tools.support_api:create_tools`: customer.get / order.get /
      refund.create / email.send), correct and wrong Python agents, and `refund-agent.yaml`.
- [x] End-to-end matrix (`tests/test_run_agent.py`): PASS, FAIL, unauthorized-tool rejection,
      invalid-arguments isolation, budget and wall-time attribution, zero residuals.

## Broker semantics

- Agents only ever see the broker (`tools.call(name, arguments)`); raw `Tool` objects stay with
  the runner.
- Every rejection raises a structured `ToolCallError` to the agent — agents may catch it and
  continue; if it escapes, it becomes the run's `AGENT_FAILURE` with the original code
  (`TOOL_NOT_ALLOWED`, `TOOL_ARGUMENT_INVALID`, `AGENT_BUDGET_EXCEEDED`, ...).
- A budget that is silently absorbed (agent catches the rejection) still produces an
  `AGENT_FAILURE/AGENT_BUDGET_EXCEEDED` failure record at the end of the agent phase.
- Event payloads are redacted by key (`authorization`, `cookie`, `token`, `password`, `api_key`)
  before being written.
- Tool results must be JSON-serializable; anything else is a structured tool failure.


## Known boundaries (deferred)

- Agents are trusted host code; nothing stops a malicious agent from bypassing the broker
  (strong isolation is a later Agent Runtime milestone).
- Coroutine cancellation on wall-time timeout is cooperative, not forced termination.
- No framework adapters (OpenAI Agents SDK, LangGraph), no multi-trial, no LLM judges.
- `fixed_clock` is accepted in `AgentContext` but always `None` in M3 (time control arrives with
  later reproducibility work).
