# Phase 2 / M6 — Acme Support World v1

M6 builds the richer eval world under `examples/acme-world/` (support-world stays frozen as the
Phase 1 reference). Stdlib-only, single service, in-memory state, deterministic reset — no new
runtime dependencies anywhere.

## Acceptance criteria

- [x] 12 business entity types (users, customers, organizations, orders, payments, refunds,
      approvals, tickets, emails, calendar, knowledge, escalations), plus the audit log.
- [x] Policy engine, all deterministic and audited: identity verification (403+AUDIT), refund
      window vs. the fixed `ACME_NOW` constant (422+AUDIT), positive-amount lower bound
      (400+AUDIT), >500 approval matching order+amount (403+AUDIT), sensitive fields redacted to
      non-admins (`[REDACTED]`), agent customer-scope isolation (403+AUDIT), irreversible
      `order.cancel` requiring `confirm: true` (400), `human.escalate` records escalations.
- [x] RBAC: `X-Actor` header required on every non-health request (401 otherwise); mutating ops
      adjudicated by `users.role` + `customer_scope`; every audit entry records the actor with
      before/after summaries; admin-only customer fields reject non-admins.
- [x] Canonicalization covers all list entities (`audit_log:sequence`, `emails:sent_seq`,
      `refunds:created_seq`, `escalations:created_seq`, `calendar:id`); export is fully
      deterministic (no wall clock — the refund window compares against the fixed `ACME_NOW`).
- [x] `env-check --cycles 20` → 20 identical digests; the same environment.yaml with the
      `overdue-refund` fixture produces a different, equally stable digest.
- [x] Smoke case `refund-smoke.yaml` runs the full loop (restore → python agent → final state →
      state_assertion + test_command graders → PASS), including an in-container grader that
      asserts every side effect carries the injected agent actor.
- [x] RBAC matrix tests (host-level, no Docker) cover every policy with positive and negative
      cases plus audit assertions.

## Determinism rules

- No wall clock reads in business logic; `ACME_NOW` and `ACME_REFUND_WINDOW_DAYS` are environment
  constants baked into the image.
- All sequence-bearing entities use per-run counters (`created_seq`, `sent_seq`, `sequence`).
- `metadata.generated_at` and `/runtime` are removed during canonicalization; every generated
  timestamp lives only under those paths.

## Known boundaries

- The provider injects a fixed agent actor (`U-AGENT-01`); per-case actor assignment arrives with
  the M9 task packs (providers are trusted case code, so a case can ship its own provider).
- `customer_scope: null` on staff/admin means "all customers"; the agent role requires a
  non-empty scope.
- List endpoints without an explicit filter show agents only their scope (customers, orders,
  tickets); an explicit out-of-scope `customer_id` filter is a hard 403+AUDIT, and direct entity
  access outside the scope is likewise 403+AUDIT.
- Approvals adjudicate deterministically in-policy (`amount <= refundable`); real reviewer
  simulation is out of scope.
- **Identity is forgeable by design.** `X-Actor` is a bare header injected by the (trusted) tool
  provider, not a credential — an agent under test may attempt privilege escalation, and that is
  the point: every mutation is audited with its actor, and the smoke grader's actor-consistency
  check catches it deterministically. Acme World is not a security boundary.
- `calendar.create` takes a free-text `owner` with no scope check — calendar events are not
  customer data in v1; revisit if M9 tasks put calendar content in scope.
- The store rewrites `db.json` on every authorized request (the request-id counter). This write
  amplification is fine at fixture scale but should be addressed (e.g. batching runtime counters
  outside the store) before M9's 20-case suite.
